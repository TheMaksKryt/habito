# Feature Specification: Walking Skeleton — рабочий каркас проекта

**Feature Branch**: `001-walking-skeleton`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "«walking skeleton»: монорепо (apps/web + apps/api), пустой Nuxt и Elysia с /health, PostgreSQL/Redis, Docker Compose, CI-гейты — всё поднимается и отвечает, но без бизнес-логики."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Запуск всей системы одной командой (Priority: P1)

Разработчик клонирует репозиторий, выполняет одну документированную команду — и вся
система (веб-приложение, API, оба хранилища данных) поднимается локально: в браузере
открывается стартовая страница-заглушка, проверка здоровья API подтверждает
работоспособность всех компонентов. Бизнес-логики нет — это «пустой холст», на котором
дальше строятся фичи.

**Why this priority**: это и есть суть walking skeleton — сквозной путь «код → работающая
система» должен существовать раньше любой функциональности. Без него ни одна следующая
фича не может быть проверена.

**Independent Test**: на чистой машине с установленными предварительными требованиями
выполнить команду запуска из документации; открыть адрес веб-приложения и endpoint
здоровья API; убедиться, что оба отвечают.

**Acceptance Scenarios**:

1. **Given** чистый клон репозитория и установленные предварительные требования,
   **When** разработчик выполняет документированную команду запуска, **Then** все
   сервисы стартуют и в течение 2 минут приходят в состояние «готов».
2. **Given** запущенная система, **When** разработчик открывает адрес веб-приложения
   в браузере, **Then** отображается стартовая страница-заглушка проекта.
3. **Given** запущенная система, **When** запрашивается endpoint здоровья API,
   **Then** ответ подтверждает работоспособность API и доступность обеих подсистем
   хранения.
4. **Given** одна из подсистем хранения остановлена, **When** запрашивается endpoint
   здоровья, **Then** ответ явно указывает, какая именно зависимость недоступна.

---

### User Story 2 - Автоматические quality gates на каждое изменение (Priority: P2)

Каждое предлагаемое изменение кода автоматически проверяется (стиль, типы, тесты)
до попадания в основную ветку. Сломанное изменение физически не может быть слито.

**Why this priority**: гейты обязаны существовать с первого коммита (Принцип VII
конституции); добавлять их «потом» — значит накопить долг до появления первой фичи.

**Independent Test**: открыть два тестовых PR — корректный и с намеренной ошибкой
типов — и убедиться, что первый проходит проверки, а второй блокируется с указанием
причины.

**Acceptance Scenarios**:

1. **Given** открыт PR с корректными изменениями, **When** автоматическая проверка
   завершается, **Then** все гейты (стиль, типы, тесты) зелёные и слияние разрешено.
2. **Given** PR содержит ошибку типов, нарушение стиля или падающий тест, **When**
   проверка завершается, **Then** слияние блокируется и причина видна в отчёте проверки.
3. **Given** зависимости изменены без обновления lock-файла, **When** проверка
   выполняется, **Then** она завершается ошибкой воспроизводимости установки.

---

### User Story 3 - Онбординг нового разработчика по документации (Priority: P3)

Новый разработчик получает только ссылку на репозиторий и, следуя README, без
устных подсказок доводит систему до работающего состояния.

**Why this priority**: проверяет полноту документации и конфигурации; ценно, но
зависит от результатов историй 1–2.

**Independent Test**: человек, не участвовавший в настройке, проходит путь
«клон → запуск» только по README и фиксирует все места, где пришлось спрашивать.

**Acceptance Scenarios**:

1. **Given** только репозиторий и README, **When** новый разработчик следует
   инструкции, **Then** локальная система запущена без обращений к другим людям.
2. **Given** отсутствует обязательная переменная окружения, **When** выполняется
   запуск, **Then** выводится понятное сообщение об ошибке с указанием на пример
   конфигурации.

---

### Edge Cases

- Нужный порт уже занят другим процессом — поведение и способ разрешения конфликта
  описаны в документации, сообщение об ошибке указывает на причину.
- Подсистема хранения недоступна в момент старта — сервисы не падают молча:
  запуск дожидается готовности зависимостей, а проверка здоровья отражает
  фактический статус.
- Перезапуск локального окружения — данные хранилищ сохраняются, система
  возвращается в рабочее состояние без ручных действий.
- Секретные значения случайно добавлены в коммит — в репозитории есть только пример
  конфигурации с заведомо фиктивными значениями; реальные значения игнорируются
  системой контроля версий.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Репозиторий организован как единое рабочее пространство, содержащее
  два приложения — веб-интерфейс и API — и выделенное место для будущих общих пакетов.
- **FR-002**: Веб-приложение отдаёт стартовую страницу-заглушку, подтверждающую,
  что система работает.
- **FR-003**: API экспонирует endpoint проверки здоровья, сообщающий собственный
  статус и доступность каждой из двух подсистем хранения (основное хранилище данных
  и хранилище для кэша/очередей) по отдельности.
- **FR-004**: Вся система (веб-приложение, API, обе подсистемы хранения) запускается
  локально одной документированной командой.
- **FR-005**: Данные подсистем хранения сохраняются между перезапусками локального
  окружения.
- **FR-006**: Каждый сервис имеет автоматическую проверку готовности; зависимые
  сервисы стартуют только после готовности своих зависимостей.
- **FR-007**: Конфигурация задаётся переменными окружения; в репозитории хранится
  пример конфигурации с заведомо фиктивными значениями; реальные секреты в
  репозиторий не попадают.
- **FR-008**: Для каждого приложения существуют команды проверки стиля, типов и
  тестов; все три выполняются автоматически на каждое предлагаемое изменение и
  блокируют слияние при неуспехе.
- **FR-009**: Установка зависимостей воспроизводима: версии зафиксированы
  lock-файлом, его рассинхронизация приводит к ошибке автоматической проверки.
- **FR-010**: В каждом приложении существует работающий тестовый харнесс минимум
  с одним осмысленным проходящим тестом.
- **FR-011**: README описывает назначение проекта, предварительные требования и
  полный путь от клонирования до работающей системы.
- **FR-012**: Каркас не содержит доменной функциональности («пустой холст»):
  ни аутентификации, ни пользовательских данных, ни бизнес-правил.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Путь от чистого клона до полностью работающей локальной системы
  занимает не более 10 минут и требует одной команды запуска (не считая установки
  предварительных требований).
- **SC-002**: Стартовая страница веб-приложения открывается в браузере сразу после
  запуска системы.
- **SC-003**: Проверка здоровья отражает фактическое состояние системы: при
  отключении любой подсистемы хранения статус меняется не позднее чем через
  30 секунд и указывает конкретную недоступную зависимость.
- **SC-004**: Автоматическая проверка изменений завершается не более чем за
  10 минут; изменение с ошибкой стиля, типов или тестов не может попасть в
  основную ветку.
- **SC-005**: Новый разработчик доводит систему до работающего состояния,
  пользуясь только README, — ноль обращений к команде за недостающими сведениями.
- **SC-006**: После перезапуска локального окружения система возвращается в
  рабочее состояние без ручных действий, данные хранилищ сохранены.

## Assumptions

- Технологический состав и структура зафиксированы конституцией проекта v1.0.0
  (Bun-монорепо `apps/web` + `apps/api` + `packages/*`, Nuxt ^4.5.1, Elysia,
  PostgreSQL, Redis, Docker Compose для локального окружения, Sentry — при первом
  деплое). Спецификация описывает результаты; выбор конкретных технологий — предмет
  плана реализации и конституции, а не этой спецификации.
- Скоуп фичи — локальное окружение и автоматические проверки изменений.
  Развёртывание на публичный сервер (домен, HTTPS, автодеплой по релизному тегу,
  бэкапы) — отдельная следующая фича согласно этапной модели конституции.
- Автоматические проверки выполняются средствами платформы хостинга репозитория.
- Предварительные требования разработчика (контейнерная среда и runtime) явно
  перечислены в README; их установка не входит в измеряемое время запуска.
- PWA-механика, push-уведомления и наблюдаемость (Sentry) в каркас не входят —
  добавляются последующими фичами по мере необходимости.
